## 1. The design decisions already taken (do not reopen; argue in the report if one is wrong)

**D1 — provider on the printer row, not on the environment.** `printers.provider` (migration **0057**) ∈ `snapwear | prodigi | fake | manual`. The dispatcher resolves the client from the ROW of the printer the order was routed to (`orders.production_snapshot_json`'s `printer` id → its row → `provider`), never from an environment switch. `DISPATCH_TARGET` is retired from the code (the var stays in `wrangler.jsonc`/`pinned.*.json` for the preflight until the reviewer removes it; the code must not read it). The five literal unions named in the handover go.

**D2 — provider gates, per environment, each fail-closed.** A client exists only when its provider's gate passes:
- `fake`: `APP_ENV = "staging"` AND `FAKE_PRINTER_TOKEN` ≥ 32 chars (the fake printer route keeps the same two conditions; the `DISPATCH_TARGET = "fake-printer"` condition goes).
- `snapwear`: `APP_ENV = "production"` AND `SNAPWEAR_SUBMIT_ENABLED = "true"` AND a bare https origin AND a well-formed token (as today, minus the DISPATCH_TARGET condition).
- `prodigi`: `PRODIGI_SUBMIT_ENABLED = "true"` AND `PRODIGI_API_BASE_URL` a bare https origin AND `PRODIGI_API_TOKEN` well-formed, AND the environment pairing: on `APP_ENV = "staging"` the origin's host MUST be `api.sandbox.prodigi.com` and the token MUST start with `test_`; on `"production"` the host MUST be `api.prodigi.com` and the token MUST NOT start with `test_`. Anything else ⇒ null ⇒ the dispatcher parks the row (existing `parkForPrinter`).
- `manual`: never a client.
A gate failing is `printer_not_configured` to the dispatcher, as today.

**D3 — several api printers may exist in one environment.** The "one api printer per environment" policy (`printersAllowedIn`, `dispatchTargetOf`, checkout's `dispatchTarget` option, the `printer_mismatch` check in `dispatch-effect.ts`, the `routing.printerId !== dispatchTarget` refusal in `pod-mappings.ts`) is replaced by a per-row policy: an `api` printer row is allowed in an environment iff its provider may exist there (`fake` → staging only; `snapwear` → production only; `prodigi` → both; `manual` → both). The SKU check of `printersAllowedIn` applies to `snapwear` and `fake` rows only (`SNAPWEAR_SKUS`); a `prodigi` row's SKUs are whatever its catalogue says. Checkout's line resolution refuses a line whose routed printer is not an active `api` row whose provider is allowed in this environment; the error names stay what they are.

**D4 — one Prodigi order per OUR order; the dispatch rows stay one per line ("leader line").** Shipping is charged per Prodigi order, so an order with three print lines must become ONE Prodigi order with three items. The outbox keeps one `dispatch` row per line (`dispatch:{orderId}:{lineNo}`, unchanged); what changes is what a row does when the printer's unit of work is the order (`PrinterClient.unit = "order"`; SnapWear and the fake stay `"line"`):
1. The row builds the job from EVERY dispatchable line of its order (lines of the same printer whose `dispatch_state` is not cancelled/superseded), with each line's print files. A sibling line whose print canvas is not ready PARKS this row exactly as its own missing canvas would (reuse the existing park).
2. If any sibling line is already `accepted` with a `printer_job_ref`, the row ADOPTS that reference: its line is marked accepted with the same reference and the row completes as `duplicate` — no HTTP call.
3. If a sibling line's row is `submitting` right now, this row is parked for a short retry (the existing backoff), never submitted in parallel. Close the race in SQL: the `claimed → submitting` transition of an order-unit row is conditioned (a `SqlGuard`, like `fenceGuard`) on NO other dispatch row of the same order being `submitting`.
4. On `accepted`, ALL included lines are marked accepted with `printer_job_ref = ord_…` in the same batch as the row's transition (so later sibling rows take path 2). `rejected`/`unknown` keep today's per-row handling; the lines not of this row are left untouched (their own rows will try and, on `AlreadyExists`, adopt).
5. `idempotencyKey = orderId`, `merchantReference = orderId`, `items[].merchantReference = String(lineNo)`. `AlreadyExists` ⇒ `duplicate` (the dispatcher's existing meaning: a lost answer was accepted) — and when the response carries the order id, record it on the lines as in 4.
6. A cancellation of one line after the Prodigi order exists is the existing `printer_cancellation` flow (a human cancels with the printer; Prodigi refuses once in production). Document it; build nothing new for it.

**D5 — `PrinterJob` reshaped once, for both shapes.** `PrinterJob { jobId, orderId, shipTo, lines: Array<{ lineNo, sku, quantity, artworks: Array<{ location, url }>, mockupUrls }> }`. The SnapWear body builder and the fake REQUIRE `lines.length === 1` (a job with more lines is `rejected` `multi_line_job`, never truncated). `jobId` stays `{orderId}-{lineNo}` for line-unit printers and is `{orderId}` for order-unit printers; `printer_job_ref` stores the printer's reference as before.

**D6 — Prodigi wire.** Base `PRODIGI_API_BASE_URL` (bare origin) + `/v4.0/orders`; header `X-API-Key`; body `{ idempotencyKey, merchantReference, shippingMethod: "Standard", callbackUrl, recipient: { name, address: { line1, line2?, postalOrZipCode, countryCode, townOrCity, stateOrCounty? } , phoneNumber? }, items: [{ merchantReference, sku, copies, sizing: "fitPrintArea", assets: [{ printArea: "front"|"back", url }] }] }`. No `branding`, no `email` on the recipient, no `metadata`. `callbackUrl = AUTH_BASE_URL + "/v1/webhooks/prodigi"`. No-redirect fetch (`redirect: "manual"`), 30 s timeout, the `PRODIGI_FETCH_OVERRIDE` symbol seam like `SNAPWEAR_FETCH_OVERRIDE`. Classifier: HTTP 200 with `outcome: "Created"` → accepted (`printerJobId = order.id`, must match `^ord_[A-Za-z0-9]+$`, bounded); `outcome: "AlreadyExists"` → duplicate; `outcome: "CreatedWithIssues"` → accepted (issues are the printer's to raise; note it in the report); 400/422 or `outcome: "ValidationFailed"` → rejected (code = the first `issues[].errorCode`/`failures` key when present, else `validation_failed`); 3xx/401/403/404/408/429/5xx or a network error → unknown. A collected order (no `shipTo`) is `rejected` `ship_to_missing` (as SnapWear). Country: ShipTo.country is already ISO alpha-2 — verify in `commerce/recipient.ts` and say so.

**D7 — Secrets and vars (names final).** `PRODIGI_SUBMIT_ENABLED` (var), `PRODIGI_API_BASE_URL` (var), `PRODIGI_API_TOKEN` (secret). Typed in `src/env.d.ts` with the same comment style as the SNAPWEAR_* block; `test/env.d.ts` likewise.

## U3. Webhook intake `POST /v1/webhooks/prodigi` (after U12; Opus)

**Goal.** Prodigi's callbacks move a line's production state forward without trusting the payload: the route takes the order id from the CloudEvent, re-reads `GET {PRODIGI_API_BASE_URL}/v4.0/orders/{id}` with OUR key, and records what that answer says through `recordProductionStatus` (the ONLY writer; `actorUserId = null`).

**Files (yours).** `$CF/src/dispatch/prodigi-intake.ts` (new), `$CF/src/dispatch/prodigi-client.ts` (add `readOrder(id)` to the client module U12 made, same fetch seam/timeout/no-redirect), `$CF/src/app.ts` ONLY inside new anchor blocks `CP11-IMPORTS-U3` / `CP11-ROUTES-U3` (an exact path, `onMethods(["POST"])`, NOT in `storefront(...)` — mirror `STRIPE_WEBHOOK_PATH`), `$CF/test/prodigi-intake.test.ts`, `docs/cf-port/CP11_U3_REPORT.md`.

**Rules.** (1) Body read under the 64 KiB cap (`lib/responses.ts` has the capped readers from the 2026-10-14 audit batch; use them). (2) Accept only `application/json` (or `application/cloudevents+json`), a CloudEvent whose `type` starts with `com.prodigi.` and whose `data.id` (or `subject`) is `^ord_[A-Za-z0-9]{1,64}$`; anything else → 404 (the opaque answer; a probe learns nothing). (3) Rate-limit by IP with `lib/rate-limit.ts` (`enforceRateLimit`, a key of its own, 60/min) → 429 with Retry-After. (4) The gate: the route exists only when the `prodigi` provider gate of U12 passes (no client ⇒ 404). (5) Re-read the order with our key; the response's `merchantReference` is OUR order id; find the order's lines whose `printer_job_ref` equals the Prodigi order id (tenant comes from the order row); refuse (404) when no line matches. (6) Map, per line (`items[].merchantReference` = line number; a shipment lists its items as `shipments[].items[].itemId`, which equals `items[].id` (`ori_…`), NOT the merchant reference — verified on sandbox order ord_1186010 on 2026-10-19; the read-back order also carries `items[].attributes {color,size}` and `shipments[].{carrier{name,service}, fulfillmentLocation{countryCode,labCode}, tracking{number,url}, dispatchDate, status:"Shipped"}`): shipment with `status` Shipped (case-insensitive) containing the item → `shipped` with `tracking { number, url, carrier: carrier.name }`; else `status.details.inProduction` ∈ InProgress/Complete, or `status.stage` Complete → `in_production`; `status.stage` Cancelled → no state change, raise the existing `printer_cancellation_needed`-style alert only if the line is accepted and not cancelled on our side (read `production-status.ts`/`cancellation.ts` and say which alert fits; do not invent a new alert kind without saying so); anything else → no-op. (7) Replay-safe: `recordProductionStatus` already refuses backwards moves and no-ops repeats; the route answers 200 whenever the re-read succeeded, whatever each line's verdict, and 503 (so Prodigi retries) only when the re-read failed (network/5xx). (8) Nothing of the payload is logged; the alert texts carry ids only.

**Tests.** Refusals first (wrong method, wrong content type, over the cap, not a CloudEvent, bad id, unknown order id, gate off, rate limit), then: a shipped callback moves one of two lines to shipped with tracking, the other stays; the same callback again is a 200 no-op; an in-production callback after shipped does not move it back; a 503 when the re-read is a 500; the payload's own `status` is ignored (a payload saying Shipped while the re-read says InProgress ⇒ in_production only).
