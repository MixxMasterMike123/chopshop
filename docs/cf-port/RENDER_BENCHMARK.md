# Render benchmark — Cloudflare Containers (PLAN §2.6, §10 CP1; DECISIONS D6)

D6 put the render service on **Cloudflare Containers** and said the benchmark runs on
Containers alone. Cloud Run is the fallback only if the memory or time limits below fail.
This file is the runnable protocol. The reviewer executes it on **staging** after the
CP1-D deploy. It also holds the numbers that exist today: a native run on a local
M-series Mac. **Those numbers are not Cloudflare numbers.** The staging table at the end
is what closes the CP1 exit criterion "render decision recorded with numbers".

---

## 1. What "the largest allowed artwork" is

Three caps, applied in this order:

| Cap | Value | Source | What happens above it |
|---|---|---|---|
| Upload | 100 000 000 B | `src/storage/object-routes.ts` `UPLOAD_SIZE_BYTES_MAX` | upload refused |
| Job download | min(original size, 200 MiB) | `render-farm-client.ts` `FARM_MAX_INPUT_BYTES`; the container's `HARD_MAX_INPUT_BYTES` | `input_too_large` |
| Profile bytes | `max_file_mb` (spec: **50 MB**) | `docs/POD_PRINT_SPEC.md` §8 "50 MB-tak" | `file_too_large` **verdict** before any decode |
| Pixels | **10 000 px** on the longest side | pipeline `MAX_SOURCE_PX`, spec §8 | `px_too_large` verdict (header read only) |

The decoder therefore never sees more than **10 000 × 10 000 px at ≤ 50 MB**. That is
the memory and CPU worst case. A 50–100 MB file costs only a download to disk and then
gets a verdict. The fixture that exercises the worst case (generated by
`cloudflare/render/bench/bench.ts --fixture largest`):

- 10 000 × 10 000 RGBA PNG, **45.5 MB**.
- A 200 px transparent border, so the trim does real work. After the trim it is
  9 600 × 9 600, which gives 975 DPI and passes the gate. The whole pipeline runs:
  decode, trim, sRGB, a 45 MB PNG encode, the alpha profile and the preview.
- A Gaussian-noise band keeps the file near the byte cap.

The "typical" fixture is 3 600 × 3 600 RGBA with a 0.9 motif (0.23 MB). It is a
realistic passing upload.

## 2. Local numbers (tonight) — **local M-series Mac, native Node, not Docker, not Cloudflare**

Setup:
- Machine: Apple M1 Pro, darwin-arm64.
- Runtime: Node v22.14.0, **sharp 0.35.4, libvips 8.18.6**. These are the exact versions
  pinned in the image.
- The real `src/pipeline.ts`, plus the sha256 pass the PUT performs. No network and no
  CPU cap.
- Docker Desktop was **not running**, so no image was built and nothing ran in a
  container (§5 has the Docker version for the reviewer).

| Run | Jobs | At once | Wall per job (min / median / max) | Drain | Peak RSS |
|---|---|---|---|---|---|
| largest | 1 | 1 | 10.7 s | 10.8 s | **539 MB** (process baseline 93 MB) |
| largest | 3 | 1 | 9.9 / 10.7 / 10.8 s | 31.4 s | 550 MB |
| largest | 3 | 3 | 10.9 / 10.9 / 10.9 s | 10.9 s | 1 179 MB |
| largest | 10 | 1 | 9.9 / 9.9 / 10.1 s | 99.5 s | 587 MB |
| typical | 1 | 1 | 0.84 s | 0.85 s | 175 MB |
| typical | 10 | 1 | 0.83 / 0.86 / 0.91 s | 8.6 s | 188 MB |

A first run on sharp 0.35.3 / libvips 8.18.3 (the old farm's version, before the libheif
advisory bump) gave the same picture within noise: largest 10.4 s / 552 MB, 10 serial
595 MB peak, typical 0.85 s.

Process start to first acquire: **105 ms**. This was the entrypoint smoke test. It is the
Node-process floor only, with no VM boot and no image pull.

How to read these numbers:
- `sharp.concurrency(1)` makes each job **single-threaded**. That is why 3 in parallel
  finish in almost the time of 1 on a 10-core laptop.
- On `standard-1` (½ vCPU) expect roughly **2–4× the local wall time**. That is about
  20–40 s for the largest artwork. Staging decides.
- Memory should transfer roughly as-is (the same libvips allocations). The caveat is
  glibc's allocator on Linux, which can fragment more than macOS's (§6).
- Ten serial largest jobs barely grew the peak (539 MB for one job, 587 MB after ten).

## 3. Staging protocol (reviewer, after the CP1-D deploy)

**Preconditions:**
- The `wrangler.jsonc` block and the `index.ts` export from `CP1_D_REPORT.md` are applied.
- Staging is deployed through `scripts/cf-deploy.sh staging`. Docker must be running on
  the deploying machine, because wrangler builds `render/Dockerfile`.
- `RENDER_FARM_TOKEN` is ≥ 32 characters, and the R2 S3 keys are set, so `/v1/render` is
  live.
- A staging tenant admin session exists, as in the CP1 live smoke.

**Fixtures:**
```
cd cloudflare/render && mkdir -p ../../.bench && BENCH_DIR=../../.bench \
  node --experimental-strip-types bench/bench.ts --fixture largest --jobs 1   # writes render-bench-largest.png
BENCH_DIR=../../.bench node --experimental-strip-types bench/bench.ts --fixture typical --jobs 1
```
Upload each copy through the normal admin flow: object upload, then
`POST /v1/admin/pod/artwork` (answers 202), then poll `GET /v1/admin/pod/artwork/{id}`.
`.bench/` is scratch; do not commit it.

**Per scenario:**

Scenarios: **A** 1 × largest, **B** 3 × largest, **C** 10 × largest, **D** 10 × typical.
Run each twice, cold and warm.

1. **Cold:** make sure no instance is running. Check the dashboard's Containers page, or
   wait ≥ 10 min after the last job: `sleepAfter` is 5 min and an idle check follows. For
   **warm**, run the scenario again within 60 s of the previous one finishing.
2. Start a log capture:
   `scripts/cf-preflight.sh staging -- tail --format json > run-<scenario>.jsonl` (the preflight adds `--env staging`).
   Container stdout appears in Workers Logs too.
3. Submit the N artworks back to back. Record **T0** as the time of each 202.
4. Poll until every artwork is `ready`. Record **T3** for each.
5. Read these from the log:
   - DO `render container woken` → `startMs`: the `startAndWaitForPorts` time, i.e. the
     cold start as the DO sees it.
   - Container `first_acquire` → `processUptimeMs`, plus its log timestamp **T1**.
   - Per job, container `job_ok`: `wallMs`, `fetchMs`, `pipelineMs`, `uploadMs`,
     `peakRssMb`, `peakIsPerJob` (1 means per job), `inputBytes`, `printBytes`.
   - API `render job metrics`: the same numbers as the API received them.
   - DO `render container stopped`: its timestamp **T4**. Running seconds for this wake
     = T4 − (DO `woken` timestamp − `startMs`).
6. Check correctness in D1 (read-only):
   ```sql
   SELECT state, attempt, error, COUNT(*)
   FROM render_jobs
   WHERE created_at > '<run start ISO>'
   GROUP BY 1, 2, 3;
   ```
   Expected: only `completed | 1 | NULL`, and no `alerts` row with
   `kind='render_job_failed'` in the window.

**Derived numbers:**
- **Cold start to first acquire** = T1 − T0 of the first job. It includes up to 5 s of
  queue batching (`max_batch_timeout: 5`).
- **Drain** = the last T3 − the first T0.
- **Cost per wake**: see §4.

## 4. Cost (Cloudflare published pricing)

Source: https://developers.cloudflare.com/containers/platform/pricing/ (page "Last
updated Aug 28, 2026", fetched 2026-09-26).
- Billing is per 10 ms while running. Memory and disk are billed on the **provisioned**
  size; CPU on **active** use only.
- Workers Paid includes 25 GiB-h memory, 375 vCPU-min CPU and 200 GB-h disk per month.
- Beyond that: memory $0.0000025 per GiB-s, CPU $0.000020 per vCPU-s, disk
  $0.00000007 per GB-s.
- Instance types (docs, limits page): `basic` is ¼ vCPU, 1 GiB, 4 GB. `standard-1` is
  ½ vCPU, 4 GiB, 8 GB.

**What one wake runs for:** the jobs, plus the idle tail. The container stops polling 120
s after its last job. The DO stops it at the first `sleepAfter` expiry (5 min after the
last DO activity) at which `/healthz` says idle. So an isolated upload keeps the instance
running for about **300 s**.

| Instance | Memory / wake (300 s) | Disk / wake | CPU / largest job (est. 40 s × ½ vCPU) | ≈ $ per isolated wake | Wakes/month inside the included memory |
|---|---|---|---|---|---|
| standard-1 | 4 × 300 × 0.0000025 = $0.0030 | 8 × 300 × 7e-8 = $0.00017 | 20 × 0.00002 = $0.0004 | **≈ $0.0036** | 90 000 GiB-s ÷ 1 200 = **75** |
| basic | 1 × 300 × 0.0000025 = $0.00075 | 4 × 300 × 7e-8 = $0.00008 | (¼ vCPU, est. 80 s) $0.0004 | **≈ $0.0012** | **300** |

- The idle tail, not the render, dominates the cost.
- Uploads inside one wake share the tail. A seller uploading 5 motifs in a session pays
  for one wake.
- DO duration while the container runs is 300 s × 128 MB ≈ 37.5 GB-s per wake:
  negligible.
- Replace the estimates with the measured running seconds and `wallMs` from §3.

## 5. The same measurement in Docker (reviewer; the local number tonight could not use it)

```
cd cloudflare/render
docker build --platform linux/amd64 -t chopshop-render:bench .
docker image inspect chopshop-render:bench --format '{{.Size}}'       # image size, bytes
mkdir -p /tmp/render-bench && chmod 777 /tmp/render-bench
# standard-1 shape: ½ vCPU, 4 GiB, no swap
docker run --rm --platform linux/amd64 --cpus=0.5 --memory=4g --memory-swap=4g \
  -v "$PWD/bench:/app/bench:ro" -v /tmp/render-bench:/bench -e BENCH_DIR=/bench \
  --entrypoint node chopshop-render:bench \
  --experimental-strip-types --disable-warning=ExperimentalWarning \
  bench/bench.ts --fixture largest --jobs 1 --parallel 1
# repeat with --jobs 3, --jobs 10, --fixture typical --jobs 10;
# --cpus=0.25 --memory=1g for the basic shape
```

- Inside the image `kernelPeakRssMb` is the real VmHWM (Linux), reset before the first
  job.
- Process cold start: time `docker run` until the `container_started` log line, with
  dummy env (`RENDER_API_URL=https://127.0.0.1:9`,
  `RENDER_FARM_TOKEN=<any 32 chars>`). Acquire then fails fast; only the start is timed.
- On an Apple-silicon Mac the amd64 image runs **emulated**. CPU times are pessimistic
  there; memory is comparable. Mark those numbers as local and emulated.

## 6. Pass thresholds (proposal) and the decision rule

| # | Criterion | Pass | Why this number |
|---|---|---|---|
| 1 | Correctness | every job `completed` at attempt 1; no `fail` report, no `lease_expired`, no `render_job_failed` alert | CP2's gate is "one outcome per input under every failure"; a clean run is the minimum |
| 2 | Memory, largest artwork | `peakRssMb` ≤ **70 %** of the instance (standard-1 ≤ 2 867 MB, basic ≤ 717 MB), with `peakIsPerJob=1`; no exit 137 in `render container stopped` | 30 % headroom for glibc fragmentation across successive jobs and for Node itself. Local peak is 0.54–0.59 GB. |
| 3 | Wall time, largest | `wallMs` ≤ **120 s**; hard fail > 300 s | 300 s was the old farm's ceiling. 120 s keeps one attempt under 20 % of the 10-min lease, so a slow job never nears expiry. |
| 4 | Wall time, typical | `wallMs` ≤ **15 s** warm | The admin waits behind a "processing" state (async since CP1-C); a few seconds of polling is the UX budget. |
| 5 | Cold start to first acquire | ≤ **30 s** median of 3 cold runs; ≤ 60 s worst | Includes ≤ 5 s of queue batching. Past a minute the upload feels broken, and the retry path (queue retry 30 s) takes over. |
| 6 | Drain, 10 × largest | ≤ **10 min** with 1 instance × 1 job | Local serial drain is 99.5 s. Above 10 min, raise `MAX_CONCURRENT_JOBS` (memory permitting; 3 in parallel peaked at 1.18 GB locally) before adding instances. |
| 7 | Cost | ≤ **$0.01 per isolated upload** at list price, from measured running seconds | The ICP's volumes (hundreds of uploads a month) must round to zero next to the platform fee. |

**Decision rule:**
- Everything passes on `standard-1`: **record Containers + standard-1**.
- Additionally, if #2 holds against basic's 717 MB, run scenarios A and C on `basic`.
  Prefer `basic` (a third of the cost) if #3 and #6 still pass there.
- #2 fails: rerun on `standard-2` (6 GiB).
- Anything fails on `standard-4`: Cloud Run, per D6.

## 7. Staging results — 2026-09-27 00:50–01:00 CEST, `chopshop-api-stg` version `2b45fd0f`, `standard-1`

Measured from the API's `render job metrics` log (the container's own numbers as the API received them), `T0`/`T3` from the submitting script, correctness from D1. Container/DO console lines did not surface in `wrangler tail` (only the API's did), so "cold start → first acquire" is derived: `(T3 − T0) − wallMs` includes queue batching (≤ 5 s), the 3 s poll interval and the DO's `startAndWaitForPorts`.

| Scenario | Instance | Cold / warm | T3 − T0 | wallMs (fetch / pipeline / upload) | peakRssMb (peakIsPerJob=1) | Derived cold start → first acquire | Pass? |
|---|---|---|---|---|---|---|---|
| A 1×largest (45.5 MB, 10 000² px) | standard-1 | **cold** (process uptime at job end 35.1 s ⇒ 0.65 s before the job) | 46.8 s | **34.5 s** (1.2 / 31.4 / 1.7) | **563 MB** | ≈ 12 s | ✅ |
| A 1×largest | standard-1 | warm (same process, job #2) | 51.1 s | 43.7 s (1.6 / 40.1 / 1.9) | **661 MB** (rss after: 352 MB, up from 283) | ≈ 7 s (poll + batching) | ✅ |
| D 10×typical (0.23 MB, 3 600² px) | standard-1 | warm | 10.6 / 11.7 / 17.0 / 20.4 / 23.8 s (serial) | 3.9–4.2 s each (≈ 3.3 pipeline) | 326–354 MB | — | ✅ (#4 ≤ 15 s) |
| B 3×largest, C 10×largest | — | not run tonight | | | | | ⏳ |

- **Correctness:** `render_jobs` in the window: `completed / attempt 1 / NULL` × 7; `alerts` empty; `pod_artwork` all `ready`. No `lease_expired`, no `fail` report.
- **Rate limit observed:** `POST /v1/admin/pod/artwork` is 5 / min / IP (`POD_DISPATCH_IP_LIMIT`), so scenario D got 5 of 10 through; the rest answered 429. By design for CP1 (flood shield); a bulk-upload UX (CP6) needs either a per-session allowance or client pacing. Scenarios B/C need pacing to 5 / min or a temporary raise — run them at CP2 with the failure-injection suite.
- **Wall time vs local:** 31–40 s pipeline on ½ vCPU vs 10.7 s on the M1 Pro = **3–4×**, exactly the §2 estimate. The warm job was slower than the cold one (40 s vs 31 s) and peaked 100 MB higher — consistent with glibc fragmentation after a 45 MB PNG encode (§6 caveat); watch `rssMb` over more jobs before adding jemalloc.
- **Cost:** running seconds for the cold wake ≈ 0.65 + 34.5 + idle tail (`IDLE_EXIT_SECONDS` 120 → then the DO's `sleepAfter` 5 min) ⇒ ≈ 6 min at standard-1 list price ≈ **$0.004 per isolated upload** (§4), under the $0.01 threshold. The idle tail, not the render, is the cost.

**Decision (D6, numbers):** **Cloudflare Containers, `standard-1`, `MAX_CONCURRENT_JOBS=1`, `sleepAfter` 5 m / `IDLE_EXIT_SECONDS` 120 kept.** `basic` (1 GiB) is **rejected**: 661 MB peak on the second largest job leaves < 8 % headroom against its 717 MB rule and the run showed growth between jobs. Thresholds #1–#5 and #7 pass; #6 (10× largest drain) is extrapolated at ≈ 6–7 min from 35–44 s per job and must be measured at CP2. Mikael approves per PLAN §11.2 (recorded in DECISIONS D6).
