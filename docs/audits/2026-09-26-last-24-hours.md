## Findings

### F1 — P1: seller can remove a platform takedown by deleting and recreating the product

**Location:** `firestore.rules:188–199`, especially the seller delete permission at line 199.

The new rules deny direct seller reactivation of a taken-down product, but still allow the shop administrator to delete it. The same administrator can then create the same document ID with the same SKU, `isActive: true`, and no moderation fields. The platform restriction disappears; the old report can remain marked taken down. Existing SKU mappings need not change.

**Evidence:** reproduced against the actual Firestore rules in a local emulator. Direct reactivation was denied; seller deletion and recreation both succeeded. The recreated product passed the actual `validateCartLine` helper. This establishes a rules and checkout-validation bypass, not a completed live payment.

**Fix:** disallow seller deletion of taken-down products, and retain a durable restriction/tombstone if moderated documents can be deleted by another workflow. Add a regression test covering delete → recreate, not just update. This closes the demonstrated same-ID bypass; detecting substantially identical uploads under new identities is a separate moderation concern.

### F2 — P2: manual POD mappings save successfully but cannot route at checkout

**Locations:** `functions/src/print/printRouting.ts:108`; `src/wagons/pod-wagon/components/ProductMapping.jsx:73–77`; `src/utils/podMappings.js:76`; `functions/src/payment/createPaymentIntent.ts:715–723`.

The manual mapping form explicitly supplies `garment: null` and has no garment selector. Its comments still promise default-printer routing. The new router instead returns null immediately for an unknown garment, even with an active default printer. Checkout rejects such a line with `no-printer-for-garment`.

This affects new manual mappings and legacy mappings without garment metadata; updating an existing studio mapping preserves its garment and is not the same failure case.

**Evidence:** traced the form → stored mapping → router → checkout rejection path; reproduced the actual router returning null with an active configured default. No live PaymentIntent was created.

**Fix:** collect or reliably infer a supported garment when creating a manual mapping, validate it before publication, and backfill legacy mappings before rollout. Update stale comments. Keep the router's explicit capability validation.

### F3 — P2: clearing the final print frame re-enables unsupported print positions

**Locations:** `src/components/platform/PrinterRow.jsx:75–90`; `functions/src/print/printRouting.ts:136` and its client capability-check counterpart.

The editor omits a garment from `printAreasMm` when its last valid frame is cleared. Capability checks interpret an absent garment entry as legacy “no capability data,” which allows print positions. Thus clearing the last frame for an offered garment changes restricted capability into unrestricted capability, despite the editor's empty-means-unavailable wording.

**Evidence:** executed the actual editor conversion helpers: clearing the last tee frame produced `{}` rather than `{ tee: {} }`. With a front-only tee, the actual routing helper rejected `left_sleeve`; after the entry was omitted, it accepted `left_sleeve`.

**Impact:** an administrator can accidentally offer an unfulfillable placement. Missing slot prices can also leave such a placement underpriced.

**Fix:** preserve an explicit empty capability map for an offered garment, or reject the configuration for active printers. Test the complete editor serialization → client/server capability round trip.

### F4 — P2: changing mapped artwork does not rerun content screening

**Locations:** `functions/src/catalog/screenProductOnWrite.ts:77–79`; `src/wagons/pod-wagon/components/ProductMapping.jsx:73`; `src/utils/podMappings.js:80–84`.

Screening reads artwork filenames/labels through POD mappings, but its trigger listens only to `products/{productId}`. The mapping editor changes `podMappings` without writing the product. A previously cleared product can therefore switch to artwork containing a configured blocked filename term without the product's screening status being reconsidered. Subsequent checkout snapshots can use the new mapping.

**Evidence:** static dependency and write-path tracing. A deployed background-trigger integration test was not run.

**Fix:** rescreen affected products when their mapping/artwork dependencies change, and tie clearance to the screened content version. Test switching artwork on an already-cleared product. Filename screening remains limited even after this dependency bug is fixed.

### F5 — P2: seller payout display ignores refunds and transfer reversals

**Locations:** `src/components/admin/OrderPaymentCard.jsx:60–63`; `functions/src/payment/connectRefund.ts:106–124`.

The new “Utbetalning till butiken” number always equals original order total minus original application fee. The refund path records refunded totals and reversal information but does not rewrite those original amounts. A fully refunded order can consequently still show a positive payout.

**Evidence:** rendered the actual card with a refunded order; total SEK 399 and application fee SEK 200 still rendered payout SEK 199. The component's calculation does not inspect refund or reversal fields. Static tracing confirms those are recorded separately by the refund handler.

**Fix:** either clearly label this as the original settlement calculation, with a separate refund/adjustment summary, or derive the current amount from recorded settlement adjustments. Cover full and partial refunds and application-fee refund policy. A calculated order amount should not imply that Stripe has completed an actual bank payout.

## Important distinctions and known unfinished work

### Screening is advisory by default

The seed sets `hardBlock: false`, and the platform UI explicitly says flagged products are still published. Screening runs after the product write; the public projection and checkout do not require clearance. The actual helpers confirmed a flagged product can remain public and checkout-valid.

This is an intentional configuration choice, separate from F1 and F4. It does **not** implement mandatory review before the first sale. Descriptions such as “pre-publish screening” or a claimed 95% risk reduction are not supported by this implementation or measured evidence. If review before sale is the intended launch protection, it needs an enforced pending-review state and checkout gate.

### Existing launch blockers, not newly discovered regressions

`docs/SnapWearDocs/LAUNCH_TODO.md` already lists unfinished print-file requirements, outbound Snapwear API order submission and stock/exception handling. Printer routing alone does not deliver an order to Snapwear. Live checkout should stay gated until that path has been exercised end to end.

Shipping cost is still a placeholder in the seed; production withholding cannot fund an unconfigured shipping charge. Refund policy, insurance, accountant setup, certificates, contractual/DPA completion, operational takedown handling, migration/reseeding and deployment ordering also remain checklist work. Treat draft documents and “built” code separately from executed launch prerequisites.

The code creates Stripe destination charges using `transfer_data.destination`. Holding the production amount in an application fee does not by itself demonstrate that later refunds or disputes are funded. This audit did not verify the live Stripe account's settings, reserves, balances or contractual loss allocation.
